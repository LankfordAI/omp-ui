# Releases and updates

This guide explains what users receive from a release and how maintainers publish one. For installation, start with [Getting started](getting-started.md). See [Architecture](architecture.md) for the boundary between the Electron desktop app and the managed `omp` binary.

## Unreleased

- You can hand one session to another as a reference. Drag a session's row from the sidebar onto a native session's composer, or type `@` and pick it under **Sessions**: it becomes a chip in the draft. When you send, the agent gets that session's title, id, machine, and the path of its saved transcript, with a note that omp's `seance` agent can read it without resuming it, so you can ask "what did the deploy session decide?" and the agent consults the transcript itself. Your message shows the chip, and it comes back with the draft like annotation chips do. Only a session on the same machine can be referenced: a joined remote instance's session, or one with nothing saved yet, is refused with a note, and moving a draft to another machine drops its references. A live session can be referenced too; the agent reads its transcript as of your prompt ([ADR-0085](adr/0085-session-references-ride-the-prompt-text.md), #984).
- You can change omp-ui's keyboard shortcuts in **Settings → Keyboard**, for example when your OS or window manager already uses one. The page lists every app action with its current shortcut: the command palette, new session, new chat, the New session dialog, Build / Plan, the console, find in session, transcript text size, Settings, undo settle, the draft stash, start in background, and hold to talk. Click a shortcut and press the new one. If it is already taken by another action, both rows say so and **Save** stays disabled until you change one. Shortcuts that text editing, the composer, or the window rely on, such as `Ctrl+C` or `Ctrl+Enter`, cannot be taken. **reset** and **Reset all** go back to the defaults. Menus, tooltips, the command palette, and the welcome screen show your shortcuts. The composer's `Enter`, `Shift+Enter`, `Mod+Enter`, `Mod+Shift+Enter`, and `Escape` stay fixed (#998).
- You can open an interactive terminal on a fleet member from the **Fleet** view, to watch `btop` or work there without leaving for ssh, including from a phone over remote access. **Terminal** on a member's row opens that machine's login shell in the main pane; **Back to Fleet** keeps it running under **Terminals**, and **Close terminal** ends the shell. Nothing persists on the member: it also ends the shell when it stops hearing from this app for 45 seconds, when this app quits, or when its owner withdraws access. A terminal needs a new fifth access rung, **Terminal**, above **Full control**: the member must turn on **Allow fleet exec**, raise **Fleet exec ceiling** to Terminal, and grant it, so no member offers one until its owner opts in. Full control still runs one bounded command and never opens a shell. The member's **Activity** lists each terminal opened, refused, and ended; what you type is never logged (#991).
- The composer's queue chip no longer stays at **parked: 1** after you **edit** the last parked follow-up out of the queue while the agent is idle. omp reports the queue's count only when omp-ui asks for the session state, and that happened only around turns, so the old count held the chip until a later turn ran. omp-ui now re-reads the count whenever omp's queue list shrinks below it (#1003).
- On a native session, an image you paste or attach is now also saved as a file the agent can use. It still reaches the model inline as before. omp-ui also writes a copy to the temp folder of the machine that owns the session and gives the agent its path, so "save this screenshot as `docs/img/login.png`" or "attach this to the PR description" work. Your message in the transcript still shows only your text and the image. The copies are removed when omp-ui quits, like attached PDFs, so a session resumed later can no longer open them. A joined remote instance running an older omp-ui still gets the image inline, without the file (#993).
- You can schedule a prompt for a native session. Choose **Schedule…** from the session's title menu or **Schedule a prompt…** in the command palette, write the prompt, and pick **Once** at a date and time, **Daily**, **Weekdays**, or **Weekly** at a time, or **Cron** with a five-field expression. The sidebar row shows a clock and the next run time, and a **Scheduled** card at the end of the transcript offers **edit**, **remove**, and **run now**. At each time omp-ui sends the prompt in Build mode, resuming the session first if it was settled or hibernated, and a snoozed session comes back to the main list when its run starts. If a run is still in progress, that time is skipped and the card says so. Times missed while omp-ui was closed run once at the next start, with a note on the card. A joined remote instance's session keeps and runs its schedule on the machine that owns it ([ADR-0081](adr/0081-scheduled-prompts-fire-on-the-owning-host-in-build.md), #987).
- You can open a remote project or session in VS Code on this computer, connected to the fleet member over Remote-SSH. Turn on **Settings → Remote instances → Open remote projects in VS Code over SSH** (off by default); then **Open in VS Code** appears on a remote project's page in the project quick-open and in a remote session's title menu, where it opens that session's worktree checkout when it has one. The row is enabled once the member has reported in and its SSH port 22 answers this computer; otherwise it stays disabled and says why, for example *SSH port 22 did not answer on studio.tailnet*. omp-ui holds no SSH keys: VS Code's Remote - SSH extension connects with your own ssh config and agent, and reports a missing extension or a failed login in its own window. Files and Terminal still open only for this computer's projects (#995).
- You can park a composer draft and finish it in another session. `Mod+Alt+S` (⌘⌥S on macOS), or **stash draft** in the composer's `+` menu (the prompt-options sheet in the compact shell), moves the whole draft — text, images, PDF documents, and annotation chips — into an app-wide **draft stash** and clears the composer. Press `Mod+Alt+S` in an empty composer, or choose **stashed drafts**, to list what you parked, newest first, with each draft's first line, attachment count, and age; `Enter` or a click moves one into this composer, and `Delete` or its ✕ removes it. The stash is kept by this window or browser and survives restarts. A PDF attached only by path, after a rewind or an edited queue entry, is read back into the stash, so the draft also works in a session on a joined remote instance (#989).
- The agent can show you an interactive document inline in the native transcript, such as a chart of results, a sortable table, a dependency graph, or a small simulator, by calling the new `omp-ui_render_html` host tool. The card has the document's title, **−**/**+** to change its height, and an expand button that opens it full size. The document follows your theme through CSS variables. It runs sandboxed in its own process with no network, storage, popups, forms, or navigation, so a document that tries to fetch a URL or open a WebRTC connection gets nothing. Cards come back when you reload or reopen the session, and on a joined remote instance's tab. **Settings → General → Run scripts in HTML artifacts** (on by default) turns scripts off and shows every artifact as a static document; a browser connected through remote access always shows them static. The card has no **Open in browser pane** button, because the pane has network access ([ADR-0082](adr/0082-interactive-html-artifacts-run-in-a-locked-webview-guest.md), #994).
- You can copy a project to another fleet member yourself. On a project's page in the project quick-open, **Copy project to…** lets you pick a joined remote instance; that machine clones the repository over HTTPS into one of its **Fleet project roots** and registers it, so it shows up with its repository key. Turn on **Also copy gitignored files** (off by default) to also send the files git ignores, such as `.env` or local config: the dialog lists each file with its size for you to untick before anything leaves this computer, and names what it leaves out (files over 1 MB, more than 8 MB or 500 files in total, symlinks, ignored folders with over 50 files such as `node_modules`). A file that names a Provider key variable is never copied; use **Roll out keys** for keys. The member writes the files into the new checkout readable only by its user and never replaces a file the clone has. The member must grant this app **Manage projects**. A private repository, or one this checkout reaches only over SSH, cannot be cloned this way, and the dialog says to ask an agent to provision the member over its own ssh instead (#992).

Once your branch has one, the sidebar row and the session title bar show a chip such as **#985 open**, which can also read **draft**, **merged**, **closed**, or **CI failing**. Click the chip in the title bar, or the pull request button among the row's hover actions, to open it in your browser. When every pull request of a session is merged, omp-ui settles the session (its row moves to **Settled**) and shows a toast with **Undo**. A session busy in a turn is settled once the turn ends. Turn this off for one session with **Settle when pull requests merge** in its title menu, or for all sessions in **Settings → General**. omp-ui reads pull requests with your GitHub CLI (`gh`), which must be installed and logged in on the machine that owns the session; it checks every minute while omp-ui has focus and every five minutes otherwise, and **Check pull requests now** in the title menu checks at once. With two or more rows selected, a selection bar replaces the sidebar footer with **Settle**, **Snooze** (with the timed choices), **Unsnooze**, **Retitle**, **Stop**, and **Delete…**. Each button counts the rows it applies to, and Retitle runs only on running native sessions. **Stop** and **Delete…** each ask once for the whole selection. A multi-row settle is one Undo. Rows on different joined remote instances can be mixed: each acts on its own machine, and any failed rows are listed together in one notice (#988).

## Choose a download

A release has exactly four distributable files. Replace `<version>` with the tag version without its leading `v`.

| Platform | Status | File | Use |
|---|---|---|---|
| Linux x64 | Supported | `omp-ui-<version>.AppImage` | Install and run omp-ui |
| Windows x64 | Unsigned preview | `omp-ui-<version>-windows-preview-x64-setup.exe` | Per-user NSIS installer |
| macOS Apple Silicon | Supported | `omp-ui-<version>-mac-arm64.dmg` | Install omp-ui |
| macOS Apple Silicon | Supported | `omp-ui-<version>-mac-arm64.zip` | Squirrel.Mac update payload |

The macOS packages are Developer ID signed and notarized. [Issue #124](https://github.com/LankfordAI/omp-ui/issues/124) closed with that acceptance verified — notarized tagged artifacts and a physical-Mac self-update — so macOS is a supported release platform. Intel Macs are not supported: the Intel build was dropped in [issue #908](https://github.com/LankfordAI/omp-ui/issues/908). On an Intel Mac, electron-updater skips arm64 files, so the update check finds no ZIP it can install and reports an error; it never installs the Apple Silicon build.

Linux uses AppImage as its sole first-party supported format. Community packages may exist, but the project does not support them. The policy and cutover history are recorded in [ADR-0011](adr/0011-appimage-only-linux-distribution.md).

Install or repair the supported Linux release without root:

```bash
curl -fsSL https://raw.githubusercontent.com/LankfordAI/omp-ui/main/packaging/install.sh | bash
```

The installer verifies the AppImage against `SHA256SUMS.txt`, writes it to `~/.local/bin/omp-ui.AppImage`, and creates the per-user desktop entry and icons. Before touching an existing install it verifies the Electron binary's system shared-library dependencies on the staged AppImage and, if any are unresolvable, stops with the exact `sudo apt install …` command to run first. The AppImage is built with the static AppImage runtime (no FUSE2 dependency), and the installer's menu entry falls back to the runtime's extract-and-run mode when the system provides no FUSE mount support.

## Understand the release files

The four distributables ship with six supporting files, for 10 release assets in total:

- `latest-linux.yml` names the AppImage and supplies its SHA-512 update metadata. The AppImage blockmap is embedded, so Linux does not publish a separate blockmap file.
- `latest.yml` names the Windows installer and supplies its SHA-512 update metadata.
- `omp-ui-<version>-windows-preview-x64-setup.exe.blockmap` supports the NSIS differential download.
- `latest-mac.yml` names the Apple Silicon DMG and ZIP, with their sizes and SHA-512 digests. The ZIP is the Squirrel.Mac update payload.
- `SHA256SUMS.txt` contains one SHA-256 line for each of the four distributables.
- `SHA256SUMS-macos-arm64.txt` covers the DMG and ZIP. The workflow creates it during platform verification, then creates the combined manifest after all platforms finish.

The SHA-256 manifests and update metadata detect corrupt or substituted bytes. They do not establish publisher identity. macOS gets publisher identity from Developer ID signing and notarization. The Windows preview has no equivalent trusted Authenticode signature yet.

### Language assets

Every package includes the English and Korean UI catalogs and the bundled Pretendard Variable Korean fallback face. The font adds about 2.06 MB to the unpacked renderer assets; it is emitted byte-for-byte into both desktop and remote-web builds. The Settings → General language choice applies locally with no additional download, while session and terminal content remain unmodified.

To verify one downloaded file, place it beside `SHA256SUMS.txt` and select only its line. For example:

```bash
grep 'omp-ui-.*\.AppImage$' SHA256SUMS.txt | sha256sum -c -
```

On macOS, verify the Apple Silicon DMG with:

```bash
grep 'omp-ui-.*-mac-arm64\.dmg$' SHA256SUMS.txt | shasum -a 256 -c -
```

Continue only when the selected file reports `OK`.

## How application updates behave

Packaged Linux, Windows, and macOS builds check their update train in the background at launch when the omp-ui launch check is enabled: the stable train, the default, reads the latest stable GitHub release, and the nightly train reads the rolling `nightly` prerelease (Settings → Updates, *Update train*). The command palette can run the check on demand. Drafts and prereleases never qualify for the stable train. Background lookup, metadata, and download failures stay silent, as do no-update results. An on-demand check reports its staging progress and failures. Development builds and builds without a valid stamped version do not check.

AppImage, NSIS, and macOS installs use `electron-updater`. A background check downloads and verifies a newer release before the update card appears:

- AppImage uses `latest-linux.yml` and its embedded blockmap.
- NSIS uses `latest.yml` and the matching `.exe.blockmap`.
- macOS uses `latest-mac.yml`; Squirrel.Mac applies the ZIP that matches the Mac's architecture.

A staged update does not install silently. `Restart now` asks for confirmation when live sessions exist, then quits, installs, and relaunches. `Install when I quit` arms the staged update for the next natural quit and can be undone. A natural quit still goes through the live-session quit guard. Once the user confirms a quit, omp-ui stops its processes; neither update choice preserves running work. After the relaunch, omp-ui reopens the tabs whose sessions were live when it quit; a session that was hibernated or had exited stays dormant in the sidebar.
On macOS, the wrapper download completes before Squirrel.Mac finishes its native preparation. After `Restart now`, omp-ui immediately displays `Applying update…` and removes the update actions. The app may remain open for several minutes while a large ZIP is prepared, then quits and relaunches automatically. A native preparation failure remains visible as an update error instead of leaving an apparently inert restart control.

`Later` on an available offer remembers that release version during background checks. After an auto-updatable package is staged, `Later` only hides the ready card; it does not remove the staged download or undo `Install when I quit`. A manual check bypasses a remembered dismissal. Switching trains clears a remembered dismissal, disarms `Install when I quit`, and re-checks quietly on the new train, so a switch always offers rather than reporting a false up to date.

### Legacy Linux installs

The project stopped publishing deb, rpm, and standalone Flatpak packages after v0.4.0. Those packages cannot find a same-format asset in current releases, so their old update path fails closed with `expected asset missing from release`.

Migrate once by running the canonical installer:

```bash
curl -fsSL https://raw.githubusercontent.com/LankfordAI/omp-ui/main/packaging/install.sh | bash
```

After migration, updates use the supported in-place AppImage path. The skipped bridge release and the reason it was safe to remove the three legacy formats are documented in [ADR-0011](adr/0011-appimage-only-linux-distribution.md).

### Managed omp updates

omp-ui updates its managed `omp` binary separately from the desktop application. It checks the npm registry at launch when that check is enabled, or on demand from `Check for omp updates`. A missing binary offers `Install`; an older binary offers `Update now`.

An optional update never downloads without that click. The one exception is the harness floor: when the installed binary is older than the version omp-ui requires (`MIN_SUPPORTED_OMP`, 18.12.3), the launch check downloads and installs the latest release automatically — the feature set the UI promises simply does not exist below it. **Auto-upgrade** on Settings → Updates opts out, and a binary pinned with `OMP_UI_OMP_PATH` is never touched. omp-ui downloads to a temporary path, verifies that the candidate runs as `omp --version`, and atomically replaces the managed copy. A failure leaves the previous binary in place. Live sessions keep the binary they already started with; only new sessions use the installed version. The omp and omp-ui launch checks have separate switches.

### Nightly builds

The [Nightly workflow](../.github/workflows/nightly.yml) is manual-dispatch only:
nothing schedules it, and no push or pull request triggers it. A dispatch resolves
its `ref` input (default `main`) to one commit and refuses it unless that commit
is reachable from `main`, `develop`, or a stable `v*` tag — a fork PR head, a
feature branch, or the rolling `nightly` tag itself never reaches a lane (issue
#627). The trusted tip is then packaged for Linux x64, Windows x64, and macOS
arm64 under the version `<latest-stable>-nightly.<UTC date>T<UTC time>.<short SHA>` —
the base follows the latest stable release, never the tree version. The files
are delivered two ways: as 14-day run artifacts, and on one rolling *prerelease*
GitHub Release named `nightly`, which each run deletes and recreates at the
packaged commit. The macOS lane receives its signing and notarization secrets
by name from each caller; no workflow uses `secrets: inherit`.
The release body lists the changes since the previous nightly: each issue or
pull request the range's first-parent commit subjects cite, with its title, or
the commit subjects themselves when no cited number resolves (issue #922).

The `nightly` release carries the update feeds a stable release carries —
`latest-linux.yml`, `latest.yml`, `latest-mac.yml`, and the NSIS blockmap — so
the nightly train's in-app check and staged installs work end to end; the
workflow asserts the feeds are present before finishing. The prerelease flag,
not feed absence, is what keeps nightlies off the stable train: the `nightly`
release stays invisible to `releases/latest`, to `packaging/install.sh`, and
to the stable train's update check. A nightly's version prefix equals the
latest stable, and on the stable train the bare stable release outranks that
same-base prerelease, so a nightly install following the stable train is
offered the stable build and returns to it; the nightly train instead ranks
each newer nightly ahead (issue #493). Staging pins electron-updater's
`allowPrerelease` to the train, because left to itself the GitHub provider
infers a release channel from the installed prerelease version and finds no
matching tag for the rolling `nightly` release.

## Publish a release

The [release workflow](../.github/workflows/release.yml) runs for every pushed `v*` tag. The [electron-builder configuration](../packages/desktop/electron-builder.yml) defines the platform targets and the explicit Windows and macOS names. `packaging/install.sh` defines the AppImage name expected by the supported Linux installer.

The tag is the release version. Each platform job strips its leading `v`, compares the result with `packages/desktop/package.json`, and runs the workspace-scoped `npm version <version> --no-git-tag-version` only when they differ. Running from the repository root updates the workspace package and its root lockfile entry together in that job's checkout. The workflow does not create another tag, commit the stamped files, or push them back to the source branch.

The jobs run in this order:

1. `prepare` runs on a GitHub-hosted runner with no checkout. It creates the GitHub release as a **draft** if it does not exist yet, with `--verify-tag`, a title equal to the version without `v`, and empty notes. A tag missing on the remote fails here and every lane is skipped. Every other job depends only on `prepare`, so the platform lanes start together once the draft exists.
2. `release-linux` runs on the org's self-hosted Linux pool (`[self-hosted, gfx1201]` — the runners register with labels `linux,rocm,gfx1201`); the container comes back warm between jobs, so the lane installs its dependencies fresh on every run. If a lane is pointed at a label no registered runner serves, it queues forever rather than failing (issue #631). It runs the repository typecheck and tests, runs the Electron-runtime `node-pty` smoke, stamps the version, builds the AppImage, and requires exactly one AppImage plus a `latest-linux.yml` that names it and contains SHA-512 metadata. It then uploads the AppImage and Linux metadata into the draft.
3. `release-notes` checks out the full history, resolves the previous tag with `git describe --tags --match "v*" --abbrev=0 <tag>^` (the `v*` match keeps the rolling `nightly` tag of issue #480 out of the range math), lists the PRs merged between the two tags, groups commits by the issue or PR their subjects reference, lifts the tag's `## Unreleased` bullets into `## Highlights`, and writes the result into the draft. The summary sentence counts keyed entries plus reference-free commits (issue #784), so it matches the row count under What's Changed even when commit subjects omit issue refs. A failure of this job never blocks publishing: a published release with no notes beats a finished release stranded in draft, where the updater cannot see it.
4. `package-macos` builds the Apple Silicon package on a `macos-15` runner; there is no Intel build (issue #908). The job installs dependencies, runs the `node-pty` smoke, stamps the version, and packages one DMG and one ZIP from the shipped `node-pty` prebuild without rebuilding it. Packaging uses the Developer ID certificate from `CSC_LINK` and `CSC_KEY_PASSWORD`. The release command disables electron-builder's built-in one-attempt notarization. A retrying `notarytool` script then submits the DMG with the Apple credentials, staples the app and DMG, and rebuilds the ZIP around the stapled app. Stapling retries transient ticket-lookup failures with the same backoff schedule (issue #856). Verification requires one thin app and `prebuilds/darwin-arm64/pty.node`, a valid Developer ID signature from `APPLE_TEAM_ID`, Gatekeeper acceptance, and a valid app staple. The validation step retries transient ticket-lookup failures with the same backoff schedule as stapling (#879). The job then uploads its DMG, ZIP, and `SHA256SUMS-macos-arm64.txt` directly into the draft; the macOS Preview and Nightly workflows call the same reusable workflow without a `release_tag` and receive the files as a `macos-package-arm64` artifact instead.
5. `test-windows` runs the core and desktop Windows test suites; `ci.yml` runs on Linux only — the self-hosted runner for same-repo events, a GitHub-hosted `ubuntu-latest` runner for fork pull requests (issue #626) — so these are the project's only Windows test coverage. `release-windows` runs beside it: it installs dependencies, runs the `node-pty` smoke against the `win32-x64` prebuild, stamps the version, and packages NSIS with certificate discovery disabled. No MSVC toolchain is installed and nothing is rebuilt. Verification requires the unpacked app, x64 native modules, and ConPTY support files. The job then requires exactly one installer, its matching blockmap, and a `latest.yml` that names the installer and contains SHA-512 metadata before uploading all three. It performs no Authenticode signing; this is the unsigned preview accepted by [ADR-0015](adr/0015-unsigned-windows-nsis-preview.md).
6. `release-manifest` depends on successful Linux, macOS, Windows, and `test-windows` jobs, and waits for `release-notes` to finish without gating on its result. It downloads exactly one AppImage, one DMG, one ZIP, and one Windows installer. It rejects duplicate or missing names, writes the sorted four-line `SHA256SUMS.txt`, and uploads it. It then calculates SHA-512 and size for both macOS files, writes `latest-mac.yml`, and uploads the feed. Before publishing it warns in the run log when the draft's body is still empty.
7. The manifest job downloads the three published update metadata files and checks their SHA-512 fields and expected distributable names. It also requires the tag version in `latest-mac.yml`. A release is complete only after this boundary check succeeds, after which the job publishes the draft (`gh release edit <tag> --draft=false`) and verifies `isDraft` is false. Until that moment the release is invisible to `releases/latest` and the releases Atom feed, so application updates and `packaging/install.sh` resolve the last completed release rather than the one still building.

Do not rename release files by hand. The updater, installer, workflow assertions, and checksum generation all depend on the names above.

### Promote develop to main

Releases ship from `main`. Land a batch of `develop` work as a pull request whose base is `main`, and merge it with a **merge commit** (`gh pr merge --merge`) — never squash or rebase. The merge commit brings `develop`'s own SHAs into `main`'s history, so right after the merge `develop` reports 0 commits ahead and 1 behind (the merge commit, later joined by the release stamps on `main`): the ahead counter then shows only work that genuinely has not landed. A squash invents a new commit that exists only on `main`, which leaves `develop` looking dozens of commits unmerged even when the trees are byte-identical, and points blame and range math at the squash instead of the real work. Merge-commit subjects carry the promote PR number, so the nightly changelog's first-parent grep resolves them as before. The PR title should still end with the issue references the promote resolves — `(#481, #507)` — for readers of `main`. When `main` carries commits `develop` lacks (version stamps, cleared highlights), merge `main` into `develop` once before opening the PR so any conflict resolves once, on `develop`.

### Write the release highlights

Each release's Highlights come verbatim from the `## Unreleased` section of this document at the tag's commit. Before cutting the tag, give every shipped change one bullet there, in [`CONTEXT.md`](../CONTEXT.md) vocabulary, citing its issue as `#N`. Clear those bullets in the same version-stamp commit that precedes the tag. The generator also drops a lifted bullet whose issues all already appear in the previous release's notes, so forgetting to clear costs a duplicate only once. A bullet may link to a document relative to this file, for example `[ADR-0026](adr/0026-glass-chrome-via-backdrop-filter.md)`; the generator rewrites each such target to `https://github.com/<owner>/<repo>/blob/<tag>/docs/<target>`, leaving absolute URLs and `#anchor` targets untouched. Keep writing them relative so the local link check in [development.md](development.md) § Documentation-only changes still applies.

Every release published before the [Release Notes](../.github/workflows/release-notes.yml) workflow existed has an empty body. Run that workflow from *Actions → Run workflow* with the release's tag and `force: true` to regenerate its notes; a run without `force` leaves human-written notes untouched.
